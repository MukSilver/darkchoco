## 2단계 · 조직 만들기

조직을 개인 계정 대신 쓰는 이유는 두 가지입니다. 한 사람이 빠져도 소유권이 남고,
폴더별 권한과 리뷰 규칙을 걸 수 있습니다.

## 3단계 · 저장소 하나로 합치기

여섯 저장소를 새 저장소 하나에 폴더로 흡수합니다. `git subtree`를 쓰면 각 저장소의
커밋 기록이 그대로 따라옵니다.

**3-1. 조직에 빈 저장소를 만듭니다.**

이름은 `darkchoco`, 공개 범위는 **Private**, README·gitignore·license는 체크하지
않고 빈 상태로 만듭니다.

**3-2. 로컬에서 뼈대를 만듭니다.**

```bash
mkdir darkchoco && cd darkchoco
git init -b main
mkdir -p packages apps skills docs .github

# 각 폴더에 자리 표시만 해 둡니다
echo "# packages\n\n공용 부품이 들어가는 자리입니다." > packages/README.md
echo "# apps\n\n각 팀원이 소유하는 도구가 들어가는 자리입니다." > apps/README.md

git add .
git commit -m "구조 뼈대"
git remote add origin https://github.com/<조직이름>/darkchoco.git
git push -u origin main
```

**3-3. 여섯 저장소를 폴더로 흡수합니다.**

```bash
git subtree add --prefix=apps/forum-crawler \
  https://github.com/minsmiths/whs4-dark.git main

git subtree add --prefix=apps/dls-observatory \
  https://github.com/60secAgo/Notion-DLS.git main

git subtree add --prefix=apps/kr-leak-alarm \
  https://github.com/60secAgo/Kr-Leak-alarm.git main

git subtree add --prefix=apps/tg-notion-report \
  https://github.com/leesubhin060-max/telegram-channel-monitor.git main

git subtree add --prefix=apps/tg-korea-alert \
  https://github.com/minsmiths/darknetzzzz_telegram.git main

git subtree add --prefix=skills \
  https://github.com/grute02/darkchoco-skills.git main

git push
```

기본 브랜치 이름이 `master`인 저장소가 있으면 `main` 자리에 `master`를 넣습니다.
브랜치 이름은 각 저장소 GitHub 페이지에서 확인할 수 있습니다.

**3-4. 원본 저장소를 정리합니다.**

원본은 지우지 말고 **Archive**로 돌립니다. 읽기 전용이 되어 실수로 거기에 커밋하는
일이 없어지고, 기록은 남습니다. 각 저장소 Settings 맨 아래 Archive this repository
에서 할 수 있습니다.

## 4단계 · 운영 규칙 심기

구조를 세운 김에 규칙도 파일로 박아 둡니다. 이걸 해 두면 나중에 말로 설명할 필요가
없습니다.

**4-1. CODEOWNERS**

`.github/CODEOWNERS` 파일을 만듭니다.

```
/apps/forum-crawler/     @minsmiths
/apps/dls-observatory/   @60secAgo
/apps/kr-leak-alarm/     @60secAgo
/apps/tg-notion-report/  @leesubhin060-max
/apps/tg-korea-alert/    @minsmiths
/skills/                 @grute02
/packages/               @grute02 @minsmiths @60secAgo @leesubhin060-max
```

**4-2. 브랜치 보호**

Settings → Branches → Add rule 에서 `main`에 규칙을 겁니다.

- Require a pull request before merging 켜기
- Require review from Code Owners 켜기

이렇게 하면 `packages/`를 건드리는 PR은 자동으로 리뷰가 필요해지고, 자기 앱 폴더만
고치는 PR은 본인이 코드 오너라 바로 머지할 수 있습니다. 앞서 정한 "공용은 리뷰,
자기 앱은 자유"가 규칙 하나로 해결됩니다.

**4-3. .gitignore**

루트에 `.gitignore`를 만들고 아래를 넣습니다. 각 앱 폴더에도 기존 `.gitignore`가
남아 있으므로 루트에는 공통되는 것만 둡니다.

```
.env
*.sqlite3
out/
output/
sessions/
snapshots/
__pycache__/
.venv/
```

**4-4. PR 템플릿**

`.github/pull_request_template.md`를 만듭니다.

```markdown
## 무엇을 바꿨나

## 확인한 것
- [ ] 토큰·onion 주소·피해 기업 실명이 커밋에 들어가지 않았습니다
- [ ] 해당 앱이 예전처럼 돌아갑니다
```

**4-5. 문서 옮기기**

이 문서와 팀 GitHub 운영안을 `docs/`에 넣습니다. 검증 기준과 크롤링 계획서도
같이 옮기면 코드와 문서가 한곳에서 버전 관리됩니다.

```bash
git add .
git commit -m "운영 규칙과 문서"
git push
```

## 5단계 · 팀원 확인

여기까지 하면 구조가 끝납니다. 마지막으로 각자 클론해서 자기 앱이 예전처럼 도는지
확인합니다.

```bash
git clone https://github.com/<조직이름>/darkchoco.git
cd darkchoco/apps/<자기_앱>
# 각 앱의 README대로 .env 채우고 실행
```

전원이 성공하면 이 단계는 끝입니다. 실패하면 대개 경로 문제이므로 각 앱의 상대 경로
설정만 손보면 됩니다.

## 이후 · 각자 이어서 하는 일

구조가 서면 그다음은 각자 자기 폴더에서 진행합니다. 서로 기다릴 필요가 없습니다.

### 성민서 · 포럼 크롤러 (apps/forum-crawler)

지금 뼈대 단계이고 프로젝트에서 가장 중요한 미완 항목입니다. 포럼 DB를 채우려면
이것이 돌아가야 합니다.

**공용 부품 작업을 기다릴 필요가 전혀 없습니다.** 노션도 ransomware.live도 쓰지
않고 HTTP도 Playwright라 공용 패키지와 겹치는 것이 없습니다. 저장소가 옮겨지면
곧바로 이어서 하면 됩니다.

이어 갈 순서는 저장소 안 `progress-log/`의 가장 최근 파일과 `docs/development-plan.md`의
M0~M6 로드맵을 그대로 따르면 됩니다. 이미 잘 정리되어 있습니다.

### 성민서 · 텔레그램 한국 알림 (apps/tg-korea-alert)

한국 관련성 판정과 Discord 알림이 이 앱의 몫입니다. `company_country_classifier.py`가
핵심이므로 여기를 계속 고도화하면 됩니다.

Kr-Leak-alarm에도 한국 관련성 판정기(`kr_filter.py`)가 있습니다. 두 판정 기준이
어긋나면 같은 사건을 두 도구가 다르게 볼 수 있으므로, 여유가 생기면 기준을 맞추는
것을 안유빈 님과 상의해 볼 만합니다.

### 이수빈 · 텔레그램 노션 반영 (apps/tg-notion-report)

보고서 생성과 노션 반영이 이 앱의 몫입니다. 주소가 정확히 일치하는 페이지만 갱신하고
후보가 0개거나 2개 이상이면 중단하는 안전장치가 이미 잘 되어 있으므로, 그 위에 보고서
품질을 올리는 쪽으로 가면 됩니다.

### 안유빈 · DLS 관측 (apps/dls-observatory)

VM과 호스트를 나눈 구조가 잘 되어 있고 문서도 갖춰져 있습니다. SQLite 스키마와 분류
추론(`infer.py`)을 고도화하는 데 집중하면 됩니다.

### 안유빈 · 한국 유출 알림 (apps/kr-leak-alarm)

세 소스와 두 축 분류가 완성되어 있습니다. 분류 기준과 대시보드를 다듬는 쪽으로
이어 가면 됩니다.

### 최현서 · 검증 스킬 (skills)

9단계 검증 파이프라인과 북마클릿이 갖춰져 있습니다. 검증 기준을 다듬고 단계별 문서를
보강하는 작업을 이어 가면 됩니다.

## 이후 · 공용 부품 추출

구조가 선 뒤에 하는 일입니다. 급한 순서대로 적었습니다. **한 번에 하나씩, 옮긴 뒤
해당 앱이 예전처럼 도는지 확인하고 다음으로 넘어갑니다.**

**dc-telegram** — 가장 급합니다. 두 텔레그램 앱이 같은 코드에서 갈라져 지금도 각자
자라고 있습니다. `collect_messages.py`가 이미 312줄 벌어졌습니다. 이수빈·성민서 두
분이 어느 판이 최신인지 정한 뒤, 로그인·채널 목록·수집을 `packages/dc-telegram/`으로
올리고 두 앱이 그것을 가져다 쓰게 바꿉니다.

**dc-notion** — 노션 래퍼가 세 벌 있습니다. Notion-DLS 쪽이 재시도와 오류 처리가 더
갖춰져 있으므로 그것을 기준으로 합치고, 토큰 규약을 `NOTION_TOKEN_FILE`로 통일합니다.

**dc-ransomfeed** — Notion-DLS와 Kr-Leak-alarm이 같은 API를 각자 긁고 있습니다.
Kr-Leak의 `collector/sources/`가 이미 `Source` 추상 클래스로 잘 정리되어 있으므로
새로 짜지 말고 그것을 승격시킵니다.

**dc-safety** — Kr-Leak의 `SafeHttpClient`를 공용으로 올립니다. 급하지 않으므로
마지막에 하고, 일정이 밀리면 최종 발표 뒤로 미뤄도 됩니다.

## 주의할 점

**공용 부품을 고치다 여러 앱이 함께 멈추는 경우**를 가장 조심해야 합니다. 그래서
4-2단계에서 `packages/`에 리뷰를 걸어 둡니다. 규칙 하나만 지키면 됩니다.
**`packages/`는 `apps/`를 절대 import 하지 않습니다.**

**최종 발표가 10월 17일**입니다. 부품 추출이 발표 준비와 겹치지 않도록, 9월 중순
이후에는 새 추출을 시작하지 않는 편이 안전합니다.
