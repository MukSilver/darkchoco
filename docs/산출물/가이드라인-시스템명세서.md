# 유출 대응 가이드라인 — 시스템 명세서 (DC-GUIDE-SYS-001)

> 판 1.0 (2026-08-28). 금정현 원안(화면 6개 · 대응 주체 3종 · 시급성 · 한국 창구)을 기반으로,
> 허문선 원안의 「허위 판정 사건은 조치를 산출하지 않는다」를 게이트로 못박은 명세입니다.

## 1. 한 문장

**샘플에서 실제로 확인된 항목에만 조치를 내고, 확인 안 된 항목에는
「이 사고 기준 조치 없음」이라고 적는다.** 이 줄을 쓸 수 있는 국내 안내문이 없습니다 —
기관 안내문은 확인 근거가 없어서 못 씁니다. 우리는 샘플을 직접 열었기 때문에 씁니다.

## 2. 게이트 — 모든 조치의 입구

| 검증 상태 (검증 DB) | gate | 화면 동작 |
|---|---|---|
| 확인됨 · 신뢰성 높음 | full | 확인된 항목 기준 조치 안내 |
| 미확인 · 신뢰성 낮음 | partial | 사실확인·예방 중심, 주장 항목은 「주장만」으로 표시 |
| 허위 | **blocked** | **어떤 조치도 만들지 않음.** 빨간 카드 하나로 끝 |

주장(claimed)은 화면에 보이되 조치의 입력이 되지 않습니다.
「이름」과 「기타」는 단독으로 조치를 내지 않습니다 — 이름은 결합 위험에서만,
기타는 실제 값으로 나눈 뒤에 조치가 붙습니다.

## 3. 데이터 계약 (guide.json + vocab.json)

조사 결과가 아니라 **팀이 직접 재서 채우는 값**이라 leak-map.json과 파일을 갈랐습니다.
그래서 화면을 기다리지 않고 지금 채울 수 있습니다.

```
item_types[9]  노션 수집 DB 「유출 항목」 select 값 그대로.
               회사 내부 자료 · 이름 · 전화 · 이메일 · 주소 · 계정 · 주민번호 · 카드금융 · 기타
               이름·기타는 purpose:null, alone:false (단독 조치 없음)
purposes[5]    계정 보호 · 사칭/피싱 방어 · 명의 보호 · 금융 차단 · 사생활 보호
stages[3]      지금 바로 · 오늘 안에 · 이후 감시/신고  (금정현 원안의 시급성 3단)
common[3]      항목과 무관하게 늘 하는 것 (통지서 보관 · 비밀번호 · 2단계 인증)
actions[19]    조치. items[](근거 항목) · purpose · stage · desk? · minutes? · why
combos[4]      결합 위험. 확인된 항목끼리만 계산 (이름+전화→사칭 피싱 등)
desks[6]       한국 창구. 금감원 · 명의도용방지 · 개인정보포털 · 118 · 분쟁조정위 · 경찰
gates[4]       2절의 게이트 표
```

## 4. 화면 (G1~G4)

| 화면 | 무엇 | 상태 |
|---|---|---|
| G1 사고 찾기 | 검색으로 좁힘. 확인 항목 많은 순 정렬 | 동작 |
| G2 대응 한 장 | 게이트 → 확인 항목 → 결합 위험 → 시급성 3단 조치(예상 소요분 합계) → 조치 없음 명시 → 창구 | 동작 |
| G3 창구 연결 | 조치가 가리키는 창구만 모아 표기. 「무엇이 털렸으니 어디로」를 묶은 국내 화면이 없음 | 동작 (G2에 통합) |
| G4 인쇄 | `@media print`로 흰 배경 한 장. 좌측 목록·도구줄 숨김 | 동작 — 다듬기 필요 |

조치가 하나도 안 나오는 사고에는 **왜 안 나오는지** 적습니다. 빈 화면을 만들지 않습니다.

## 5. 문장 규칙

- 합니다체. 쉬운 용어. 한 조치 = 한 동사.
- 조치마다 **왜**를 한 줄 답니다 (「회사 계정만 바꾸면 개인 계정이 남습니다」).
- 「이 사고 기준 조치 없음」은 반드시 범위를 답니다 — *샘플에서 확인되지 않았다는 뜻이지 전체에 없다는 뜻이 아닙니다.*
- 72시간을 일괄 마감으로 쓰지 않습니다. 법령 요건 해당 여부를 확인하는 판단 단계로 둡니다.
- 조치 문구는 배포 전에 개인정보보호위원회·KISA 안내와 대조합니다.

## 6. 범위 결정

**이번 판은 개인 갈래만.** 금정현 원안의 대응 주체 셋(개인 · 피해 기업 · 협력사) 가운데
개인만 화면으로 만듭니다. 기업(화면 5)·협력사(화면 6)는 다음 판에서 `branch` 값 둘로
들어갑니다 — actions에 이미 branch 필드가 있어 스키마 변경 없이 확장됩니다.
협업처에 먼저 말할지 화면에서 보게 둘지는 미결(OI-1)입니다.

## 6-1. 사이트 구조

URL·상태·로딩·배포·보안은 **`사이트-구조.md`(DC-SITE-001)** 를 따릅니다.
가이드 고유의 것만 적습니다.

- `?case=N`을 지도와 **같은 뜻으로** 읽습니다. 이 값이 세 산출물을 잇는 유일한 키이고,
  노션 수집 DB의 「사건 ID」와 같은 값입니다
- `leak-map.json`에서 `cases`와 `meta`만 씁니다(`places`·`flows`는 안 씀).
  다만 gzip 15KB라 파일을 쪼개지 않습니다 — 쪼개는 이득보다 계약이 갈라지는 손해가 큽니다
- 사고 상세 `/guide/?case=N`이 **세 구역이 모이는 교차로**입니다.
  확인된 항목 → 조치 → 그 사고의 경로만 그린 축소지도 → 「어떻게 확인했나」 접힘 블록
- **가이드 → 위키 직결은 만들지 않습니다.** 일반인 동선에 다크웹 문서를 끼우지 않습니다
- 인쇄는 A4 기본, 87mm는 `body.receipt`로 가릅니다

## 7. 검사 (TC)

- TC-1 조치가 가리키는 항목·목적·창구가 전부 존재하는가 (0단계에서 검증 완료)
- TC-2 허위 사고에 확인 항목이 있으면 콘솔 경고 (shell.js validate)
- TC-3 item_types 아홉이 노션 select 값과 문자 단위로 같은가 (빌드 시 검사)
- TC-4 이름·기타에 단독 조치가 걸려 있지 않은가

## 8. 미결 (OI)

- OI-1 기업 갈래 제외를 협업처(국민일보 · 케이프랩스)에 먼저 말할지
- OI-2 허문선 원안의 조치별 체크박스 + 완료 진행률(사건별 저장) — 넣을지. 리서치 판정 후 결정
- OI-3 의료·민감정보 항목 — 노션에 값이 없어 지금은 「기타」. 노션에 값을 더하면 항목이 열이 됨
- OI-4 조치 19개의 문구를 KISA·개보위 안내와 대조하는 작업 미시작
- OI-5 창구 6곳의 번호·URL(118·1332 등)을 데이터 상수로 모아 발표 전 일괄 검증.
  안 하면 인쇄물에 죽은 창구가 박제됩니다
- OI-6 조치 19·창구 6을 팀이 손으로 채우는 일정이 없음. 늦으면 화면만 있고 내용이 빔
