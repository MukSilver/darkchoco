# 3회차 수집 기획

2회차 결과(2026-08-23, 506사이트)를 근거로 세운 계획입니다.
숫자는 전부 `dls.sqlite3` 에서 뽑은 실측치입니다.

---

## 지금 어디에 막혀 있나

| | 수 | 뜻 |
|---|---|---|
| 접속됨 | 124 | 여기서만 페이지 정보를 얻는다 |
| 죽음 | 379 | 이름·API 로만 채울 수 있다 |
| 인계됨 | 3 | 압수 또는 제3자 인수 |

접속된 124곳 중:

- **99곳이 내부 링크를 2개 이상** 갖고 있다 → 한 겹 더 들어갈 수 있다
- **35곳은 첫 화면 텍스트가 200자 미만인데 링크는 있다** → 내용이 한 클릭 뒤에 있다
- 7곳이 대기 화면(`Loading...`, `One moment, please...`, `Access Queue`)에 걸렸다
- 16곳이 가입·로그인 벽

**3회차의 목표는 "더 많은 사이트"가 아니라 "한 겹 더 안쪽"이다.**
새 사이트를 찾는 게 아니라, 이미 닿은 124곳에서 못 읽은 것을 읽는다.

---

## 1. 하위 페이지 크롤링 ← 핵심

랜딩 페이지 한 장만 읽는 지금 구조가 가장 큰 병목이다.
`FREDDY` 는 링크 25개에 본문 0자, `CHANG'AN` 은 링크 69개에 105자다.

**대상** 접속된 곳 중 내부 링크 ≥2 (99곳). 가입벽이 있는 16곳은 제외한다.

**규칙**

- **같은 onion 호스트 안의 링크만** 따라간다. 다른 onion 도, 클리어넷도 안 간다.
- 깊이 1단계. 하위 페이지에서 또 링크를 타지 않는다.
- 사이트당 최대 3개.
- 경로 우선순위: `/victims` `/leaks` `/posts` `/blog` `/news` `/archive` `/all`
  → 없으면 링크 텍스트에 `victim` `leak` `post` `news` `data` 가 든 것
  → 그것도 없으면 링크 순서대로 앞에서 3개
- **Content-Type 필터를 그대로 적용한다** (`text/html`, `text/plain`, `application/xhtml`).
  이게 유출물 아카이브를 받지 않게 막는 코드 차원의 방어선이다. 하위 페이지는
  `.zip` `.7z` 링크가 훨씬 많으므로 오히려 여기서 더 중요하다.
- 응답 본문 상한을 둔다(예: 512KB). 넘으면 끊고 버린다.

**비용** 507 랜딩 + 약 300 하위 = 약 800 요청. 3시간 → 4.5~5시간.
`--resume` 이 있으므로 나눠 돌릴 수 있다.

## 2. 본문을 VM 밖으로 내보내지 않고 추론에 쓰기

지금 추론기는 `title` `h1` `meta` `keywords` 만 본다. 그런데 다크웹 사이트는
SEO 태그를 안 쓴다 — meta 23%, keywords 18% 뿐이다. 정작 본문은 해시만 뜨고 버린다.

본문을 `probe.json` 에 담으면 추론은 좋아지지만 **피해자 회사명이 호스트로
넘어온다.** 지금까지 지켜온 "유출 대상은 저장하지 않는다" 원칙이 깨진다.

**해법: 추론을 VM 안에서 끝내고 판정 결과만 내보낸다.**

`infer.py` 를 `tor_probe.py` 와 함께 VM 에 올린다 (둘 다 표준 라이브러리만 쓰므로
그대로 돌아간다). VM 이 본문 전체를 메모리에서 매칭하고, 내보내는 건 이것뿐이다:

```json
"format_hint":  "카딩",
"format_why":   "본문 'fullz'",
"pii_hint":     "있음",
"dist_hint":    ["최초 유출"]
```

근거 문자열은 **매칭된 단어 자체만, 40자 제한**이다. 문장을 통째로 담지 않는다.
본문은 VM 메모리에서만 존재하고 디스크에 닿지 않는다.

호스트의 `dls_fill.py` 는 이 힌트를 페이지 신호와 같은 등급으로 받아
기존 우선순위(본문 → 이름 → 그룹 설명)에 넣는다.

## 3. 스키마 보강

`tor_probe` 가 뽑는데 DB 에 칼럼이 없어 적재 때 버려지는 것들:

| 추가할 칼럼 | 무엇 | 왜 |
|---|---|---|
| `final_url` | 리다이렉트 최종 주소 | 20곳이 리다이렉트되는데 **어디로 갔는지 저장을 안 한다.** 주소 이전을 잡을 신호다 |
| `subpages` | 읽은 하위 경로 (JSON) | 무엇을 근거로 판정했는지 되짚기 위해 |
| `format_hint` / `pii_hint` / `dist_hint` | 위 2번 결과 | |

`db.py` 의 `_migrate()` 가 `ALTER TABLE` 로 붙이므로 기존 데이터는 보존된다.

## 4. 오탐 두 개 수정

**Telegram 핸들 오인 (33건 중 8건).**
`Telegram: Contact`, `Telegram: Messenger`, `Telegram: channel` 은 t.me 의
시스템 경로를 핸들로 읽은 것이다. 제외 목록으로 거른다:
`contact` `messenger` `channel(s)` `share` `joinchat` `s` `iv` `addstickers`
`proxy` `socks` `login` `about` `apps` `faq`.

**대기 화면 7곳.**
제목이 `Loading` / `One moment` / `Just a moment` / `Access Queue` / `Checking
your browser` 면 5초 쉬고 1회 재요청한다. `Set-Cookie` 를 받았으면 그 쿠키를
물고 재요청한다 (DDoS-guard 계열이 이 방식이다).
**캡차는 여전히 안 푼다** — `payoutsking`, `kyber` 는 존재만 기록하고 넘어간다.

## 5. 대상 목록 다루기

실패 사유를 보면 379곳 중 **294곳이 "호스트 도달 불가"** 다. onion 서비스
설명자 자체가 없다 — 주소가 사라진 것이지 잠깐 죽은 게 아니다.

두 회차 모두 offline 인 곳이 369, 상태가 뒤집힌 곳이 22곳이다.

그래도 **전부 계속 확인한다.** 8/23 에 12곳이 되살아났는데, 그중엔 두 회차
연속 죽어 있던 곳도 있다. "계속 죽어있다"도 관측이고, 목록에서 빼면 부활을
영영 못 잡는다. 다만 도달 불가로 확정된 곳은 **재시도 횟수를 1회로 줄여**
시간을 아낀다.

## 6. 바뀌지 않는 안전 원칙

3회차에서도 이건 그대로다. 하나라도 어기면 설계가 무너진다.

- `socks5h` 만 쓴다 — DNS 를 Tor 에 위임해 호스트가 onion 이름을 조회하지 않게
- 수집 전 Tor 연결 검증. 확인 안 되면 시작하지 않는다
- Content-Type 필터 — 유출물 아카이브를 받지 않는다
- **응답 본문을 디스크에 쓰지 않는다** (3회차에는 오히려 강화된다: 추론까지
  VM 에서 끝내고 판정만 내보낸다)
- 가입·로그인 벽 뒤로 들어가지 않는다. 존재만 기록한다
- 캡차를 풀지 않는다. 제3자 풀이 서비스를 쓰지 않는다
- 피해자 회사명을 저장하지 않는다. 집계 수치만 남긴다
- DB 는 호스트에만 둔다. VM 은 `probe.json` 하나만 만든다

## 작업 순서

1. `tor_probe.py` — 하위 페이지 크롤링 + 대기화면 재시도 + Telegram 필터
2. `infer.py` — VM 에서도 돌도록 분리 확인 (이미 표준 라이브러리만 씀)
3. `db.py` — `final_url` `subpages` `*_hint` 칼럼 추가
4. `dls_db.py` — export 에 새 필드 포함
5. `dls_fill.py` — 힌트를 추론 우선순위에 편입
6. VM 에 `tor_probe.py` + `infer.py` + `targets.csv` 올리고 수집 (4.5~5시간)
7. 호스트에서 적재 → 검토 → 반영

1~5 는 제가 하고, 6 은 사용자가 VM 에서 돌립니다.
